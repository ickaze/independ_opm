# 04〜07録音の解析と0.9実装

4MHz、96kHzの提供WAVを、変更していない診断MDXの区間順と照合しました。04は16区間、05は32区間、06は8区間を無音から検出。07は連続発音のため開始点と4.194304秒の予定周期で4区間に分割しました。以下の遅延は右−左で、正が右の遅れです。

ALG7の独立正弦波でもALG5と同じ群分けが現れました。M1は全chで遅れる側です。単一正弦波は広帯域信号より絶対遅延の識別力が低く、窓・周波数ビンの影響もあるため、ナノ秒桁を物理精度とは扱いません。探索は±50µsに限定しています。

C1+C2は同じタイミング群なので、単一遅延で残差約0.001%まで一致しました。M2を含むペアの残差は約1.16〜2.93%。異なるキャリアの時間差を分ける必要性を支持します。全DT1=0でも群間の違いは残るため、DT1自体が左右出力を切り替えるモデルにはしていません。残差は左右信号間のモデル適合度であり、実機とエミュレータの一致度ではありません。

## 07LOAD: 現段階では負荷によるタイミング変更を採用しない

単独発音→他ch発音・出力無効→他ch出力有効→他ch出力無効の4区間です。全体への単一遅延の推定値は約−0.30、−0.46、−2.09、−1.85µsですが、残差は4.25〜4.79%あります。複数タイミング群が混ざるうえ、持続音の位相・うなり・音量構成も時間で変わるため、この推定値を内部タイミングの変化とは解釈できません。他ch有効時はch0以外も混ざり、ch0の遅延を分離した結果ではありません。負荷依存の有無は未確定です。

これをさらに切り分けるには、ch0を単一OP正弦波・一定レベルにして、他chは出力無効のままキーオン/オフする対照試験が有効です。今回の混合音に合わせて負荷依存遅延を追加することはしていません。

## 実装と範囲

`set_measured_output_timing(true)`でALG5/ALG7を有効化します。左は全キャリアの前回値、右はch0〜6でM1/M2のみ前回値、ch7でM1/C2のみ前回値とします。他の右キャリアは今回値です。キャリアマスクに従うためALG5のM1は出力されません。旧`set_measured_alg5_timing`は互換エイリアスで、同じ両ALGモードを有効化します。

CLIの`--gmc-opt04-4mhz`は4MHz・96kHzに限定し、共通取り込み遅延として右をリサンプル後に1フレーム遅らせます。APIにはこの共通遅延を含めません。既定で無効、明示的な非ゼロのch別マスクが優先、resetで解除。ALG0〜4/6は未検証のため拡張しません。

これは観測した出力フレーム関係のモデルであり、32OPの内部演算スケジュールそのものを復元した実装ではありません。元の音色と診断MDXのM1/M2が異なる件も、0.8報告の訂正を引き継ぎます。

## 再実行と検証

```
python -m pip install numpy scipy
python measurements-4mhz-04-07/analyze.py /path/to/wavs --output metrics.json
```

入力名は04PITCH.wav〜07LOAD.wav。96kHz/24bitを前提とする解析です。窓の先頭・末尾200msを除外、Hann窓、80Hz〜15kHz、左の最大スペクトル振幅の2.5%以上のビンで、実数ゲインと±50µsの遅延を最小二乗推定します。全区間の時刻・設定・推定値はmetrics.jsonに収録。GCC C++17で既存3テスト群と全ALG×全chの測定モード検証を通過。Windows/MSVCは未検証です。
